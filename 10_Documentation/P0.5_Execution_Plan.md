# خطة تنفيذ P0.5 — حوكمة الذاكرة والمعرفة
**P0.5 Execution Plan — Memory & Knowledge Governance**

**التاريخ:** 2026-08-06  
**الحالة:** تخطيط معتمد — التنفيذ لم يبدأ  
**النطاق:** توثيق خطة التنفيذ فقط (بدون تعديل كود)

---

## 1) الهدف

تثبيت تصميم تنفيذي آمن وقابل للتوسع لطبقات الذاكرة والمعرفة في P0.5، مع ضمان:

- فصل هوية أمير عن ذاكرة المؤسسة.
- منع أي كتابة مباشرة إلى Founder Memory دون موافقة.
- فصل Core Knowledge عن Learned Knowledge ضمن حوكمة صريحة.
- الحفاظ الكامل على التوافق مع مخرجات P0.4.

---

## 2) طبقات الذاكرة المعتمدة (النسخة النهائية)

1. 🔒 **Core Identity**  
   (الدستور، الشخصية، فلسفة الحوار، قواعد الحوكمة، أسلوب التواصل)

2. 🧠 **Core Knowledge**  
   (المعمارية الأساسية، الوكلاء، الأدوات، قواعد العمل، قدرات أمير الأساسية)

3. 📚 **Learned Knowledge**  
   (أنماط العمل المكتسبة، الخبرات التشغيلية، أفضل الممارسات، الدروس المستفادة، الملاحظات التنفيذية)

4. 👤 **Founder Memory**  
   (بيانات المؤسسة، التفضيلات، الأهداف، المشاريع)

5. 💬 **Working / Session Memory**  
   (سياق الجلسة والمهام المؤقتة والملخصات التشغيلية)

---

## 3) سياسات الحوكمة لكل طبقة

### 3.1 Core Identity
- لا تُعدل تلقائيًا.
- لا تتأثر بالمحادثات اليومية أو التعلم الذاتي.

### 3.2 Core Knowledge
- معرفة أساسية ثابتة.
- لا تتغير تلقائيًا إطلاقًا.
- أي تعديل عليها يتم فقط عبر تحديث معتمد صراحةً من المؤسسة.

### 3.3 Learned Knowledge
- تستقبل المعرفة الجديدة المكتسبة أولًا.
- لا تعدّل Core Identity.
- لا تعدّل Core Knowledge.
- تخضع لسياسة تعلم واضحة.
- قابلة للمراجعة والحذف.

### 3.4 Founder Memory
- لا كتابة مباشرة إليها.
- أي إدخال جديد يمر عبر مسار تصنيف/أهمية/موافقة قبل الحفظ.

### 3.5 Working / Session Memory
- مؤقتة وتشغيلية.
- يمكن حذفها أو إعادة بنائها دون تأثير على Core Identity أو Core Knowledge أو Founder Memory.

---

## 4) تعريف Memory Item (إلزامي)

كل عنصر مرشح للحفظ يُعرّف ككيان يحتوي على الأقل:

- `memory_type`
- `content`
- `source`
- `timestamp`
- `confidence`
- `approval_state`

قاعدة إلزامية: لا يُسمح بالترقية من Session/Working إلى Founder Memory إلا عبر ApprovalGate.

---

## 5) سياسة الخصوصية قبل التخزين

لا يتم التخزين التلقائي للفئات التالية:

- التفضيلات الشخصية
- المعلومات الصحية
- المعلومات المالية
- العلاقات
- الروتين

ولا تُخزّن إلا إذا:
1) صُنفت كمرشح ذاكرة مهم،  
2) عُرضت على المؤسسة،  
3) تم الحصول على موافقة صريحة،  
4) سُجلت مع `Source` و`Timestamp` و`Confidence` و`Approval State`.

---

## 6) مسار الحفظ المعتمد (Founder-Safe Flow)

```
Candidate Memory
        ↓
Memory Classifier
        ↓
Memory Importance Score
        ↓
Needs Approval?
      ↓        ↓
     Yes       No
      ↓         ↓
ApprovalGate   Store
      ↓
Approved?
   ↓      ↓
 Yes      No
 ↓         ↓
Store    Discard
```

قاعدة صريحة: لا توجد أي كتابة مباشرة إلى Founder Memory.

---

## 7) P0.5.1 — Knowledge Governance (إضافة معتمدة)

### الفصل بين Core Knowledge وLearned Knowledge

- **Core Knowledge**: معرفة أساسية مستقرة لا تتغير تلقائيًا.
- **Learned Knowledge**: معرفة مكتسبة تنمو تدريجيًا لكنها لا تملك صلاحية تعديل الطبقات الأساسية.

### سياسة الترقية (Promotion Policy)

- كل معرفة جديدة تذهب أولًا إلى **Learned Knowledge**.
- الترقية من **Learned Knowledge → Core Knowledge** ممنوعة تلقائيًا.
- لا تتم الترقية إلا بقرار صريح من المؤسسة.
- كل عملية ترقية تُسجل في **Governance Log** وتتضمن: من/إلى، السبب، المعتمد، التاريخ.

---

## 8) معايير القبول (Acceptance Criteria)

لن يعتبر P0.5 مكتملًا حتى تتحقق جميع الشروط:

1. جميع عناصر Founder Memory تمر عبر ApprovalGate.
2. لا توجد كتابة مباشرة إلى Founder Memory.
3. كل عنصر محفوظ يحتوي على: Source, Timestamp, Confidence, Approval State.
4. يمكن حذف أي عنصر محفوظ لاحقًا دون التأثير على بقية النظام.
5. يبقى النظام متوافقًا بالكامل مع بيانات P0.4 الحالية.
6. تبقى هوية أمير مستقلة تمامًا عن ذاكرة المؤسسة.
7. تبقى خبرات وقدرات أمير الأساسية مستقلة عن المحادثات اليومية.
8. لا يستطيع التعلم الذاتي تعديل Core Identity.
9. لا يستطيع التعلم الذاتي تعديل Core Knowledge.
10. كل معرفة جديدة تُسجل أولًا في Learned Knowledge.
11. لا تتم الترقية إلى Core Knowledge إلا بقرار صريح من المؤسسة.
12. جميع عمليات الترقية تُسجل في Governance Log.
13. يبقى الفصل صارمًا بين الطبقات الخمس دون اختلاط وظيفي.

## 9) التحقق من النجاح (عند التنفيذ لاحقًا)

### 9.1 بيئة التطوير
- اختبارات وحدة لمسار التصنيف/الأهمية/الموافقة/الحفظ.
- اختبارات تكامل تمنع الكتابة المباشرة إلى Founder Memory.
- اختبارات تحقق من الفصل بين Core Identity وCore Knowledge وLearned Knowledge.
- اختبارات توافق مع بيانات P0.4.

### 9.2 الإنتاج
- تحقق Post-Deploy من استمرار الاستقرار بعد restart/redeploy.
- تحقق من التزام Founder writes بمسار الموافقة.
- تحقق من عدم وجود Regression في سلوك Executive Brain وGovernance.

---

## 10) القيود الحالية

- لا يبدأ تنفيذ P0.5 قبل موافقة صريحة جديدة من المؤسسة.
- هذه الوثيقة تخطيطية فقط ولا تمثل بدء تنفيذ.
