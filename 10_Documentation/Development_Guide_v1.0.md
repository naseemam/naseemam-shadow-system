## 2. أثناء التطوير

### قواعد الكود

- لا تكسر نقاط النهاية القائمة: `/health`، `/ask`، `/docs`، `/projects`.
- PORT وOPENAI_API_KEY تأتي دائمًا من متغيرات البيئة — لا أسرار في الكود.
- لا تكشف أسماء الوكلاء، مسارات الملفات، أو البنية الداخلية في أي رد.
- الرد النهائي للمستخدم يمر دائمًا عبر Response Composer كآخر طبقة.
- Guardian يُفعَّل قبل أي Provider — هذا الترتيب غير قابل للتعديل.

### قواعد الذاكرة

- لا كتابة للذاكرة الدائمة إلا بطلب صريح من المؤسسة.
- أي ذاكرة جديدة يجب أن تحمل: المصدر، المالك، التاريخ، وحالة الموافقة.

### قواعد الهوية

- أمير يتحدث دائمًا بصوت أمير — لا يتغير الأسلوب بتغير الموضوع أو اللغة.
- لا يظهر JSON داخلي في أي رد للمستخدم.
- لا يظهر Prompt أو أي معلومات من النظام الداخلي.

## 3. قبل دمج أي PR

تحقق من كل البنود التالية قبل الدمج:

### الاختبارات
- [ ] اجتازت جميع الاختبارات في `07_Tests/`.
- [ ] الخادم يبدأ بلا أخطاء محليًا.
- [ ] `/health` يستجيب.
- [ ] `/ask` يستجيب خلال وقت معقول.
- [ ] لا يوجد crash بعد عدة طلبات متتالية.

### الهوية والأمان
- [ ] لا يوجد تسريب لهوية الوكلاء الداخليين.
- [ ] لا يوجد تسريب لمسارات الملفات أو البنية الداخلية.
- [ ] لا يوجد JSON داخلي أو Prompt في ردود المستخدم.
- [ ] لا توجد أسرار (API keys, tokens) مدمجة في الكود.

### الحوكمة
- [ ] لا يوجد تجاوز للدستور أو العقود الدستورية.
- [ ] لا يوجد تعديل على Architecture Freeze إلا بقرار ADR معتمد.
- [ ] يوجد مرجع واضح للتغيير (رقم المرحلة P0.x أو ADR إن وجد).

### الواجهة (إذا كان التغيير يمس الواجهة)
- [ ] RTL كامل.
- [ ] يعمل على Chrome وEdge.
- [ ] Enter للإرسال، Shift+Enter لسطر جديد.
- [ ] مؤشر حالة الاتصال يعمل.

## 4. بعد الدمج

بعد دمج أي PR ناجح:

| الإجراء | متى؟ |
|---|---|
| تحديث `CHANGELOG.md` | بعد كل دمج |
| تحديث `Production_Roadmap.md` | عند اكتمال مرحلة أو مهمة كاملة |
| إنشاء Git Tag | عند إصدار رسمي (مثلاً `v1.0.0-P0.1`) |
| تحديث Release Notes في `10_Documentation/` | عند كل إصدار رسمي |
| مراجعة ADR | إذا كان التغيير يؤثر على قرار معماري قائم |

## 5. بوابة القبول النهائية قبل النشر (Gate P0.x)

قبل الضغط على Deploy لأي مرحلة، يجب اجتياز هذه البوابة:

### Runtime
- [ ] الخادم يبدأ بلا أخطاء.
- [ ] `/health` يعمل دائمًا.
- [ ] `/ask` يستجيب خلال وقت معقول.
- [ ] لا يوجد crash بعد عدة طلبات متتالية.

### Chat UI
- [ ] RTL كامل.
- [ ] يعمل على Chrome وEdge.
- [ ] Enter للإرسال، Shift+Enter لسطر جديد.
- [ ] حالة الاتصال تتحدث تلقائيًا.

### Executive Core
- [ ] أمير يجيب كأمير.
- [ ] لا تظهر أسماء الوكلاء.
- [ ] لا تظهر أسماء الملفات.
- [ ] لا يظهر Prompt.
- [ ] لا يظهر JSON داخلي.
- [ ] لا يتغير صوته أو هويته.

### Governance
- [ ] لا كتابة للذاكرة إلا بطلب صريح.
- [ ] أوامر الرفض تعمل.
- [ ] Guardian يعمل قبل أي Provider.
- [ ] Response Composer هو آخر طبقة دائمًا.

### Deployment
- [ ] PORT من البيئة.
- [ ] OPENAI_API_KEY من البيئة.
- [ ] لا يوجد أي Secret داخل الكود.
- [ ] HTTPS يعمل.

**إذا لم تُجتز أي نقطة من هذه البوابة، لا يتم النشر.**

## 6. طريقة العمل مع Copilot

من هذه النقطة فصاعدًا، الطلب الصحيح لـ Copilot هو:

> **"راجع المرجعيات أولًا، ثم نفّذ فقط ما تسمح به الوثائق المعتمدة، وقدّم تقرير المطابقة قبل كتابة أي كود."**

Copilot جزء من حوكمة المشروع، لا مجرد مولد كود.

### ما يعنيه هذا عمليًا:
1. قبل أي تنفيذ، تُحدَّد المرحلة والمرجع من الهرم المرجعي.
2. أي تعارض مع الدستور أو ADR يُرفع للمؤسسة قبل المتابعة.
3. لا كود يُكتب خارج نطاق المرحلة الحالية.
